lc

A LeetCode workflow that lives in your notes. One command imports a problem, starts a clock, and scaffolds the code; another publishes everything to a Git repo and schedules the review.

Why it exists

Practising algorithm problems produces two artefacts that want to live in different places. The thinking — why this pattern, what the invariant is, what you got wrong — belongs in notes you'll actually reread. The code belongs in a repo. Keeping both in sync by hand means you stop doing one of them within a week.

The design decision everything hangs off

The note is the source of truth. You write in Obsidian; the repo is generated. That's the only way the notes stay current, but taken naively it's dangerous: a sync that always trusts the note will happily overwrite real code with an untouched starter stub.

So the reconciliation rule is narrower than "note wins":

note has real code   →  note wins, repo is rewritten
note has the stub    →  repo wins, and the code is written BACK into the note
neither has code     →  skip the problem entirely

That middle case is what makes "note wins" safe to say out loud, and it is where most of the 94 tests point.

Things that turned out to matter

  • Rendering lives in exactly one place. The Obsidian templates are thin wrappers that shell out to lc new --print, so note formatting can't drift between the terminal and the editor.
  • Refuse to guess. NeetCode uses different slugs than LeetCode (duplicate-integer is contains-duplicate). Rather than fuzzy-matching, an unknown slug fails with candidates and a command to teach it the mapping. A wrong problem silently imported is far worse than an error.
  • Spaced repetition, not a streak. Each solve schedules the next review on a ladder that depends on difficulty and how many times you've solved it — and marking a problem as solved-with-help pulls it back sooner.
  • A study session is derived, not authored. lc session reads the notes and builds a timed block: a recall quiz, everything you solved with help, every review that's due, and the next problems off a roadmap. Nothing to decide at 9pm.
  • macOS /bin/bash is 3.2. "${@:2}" collapses to one argument there. Found the hard way.

Shape

lc new <url|slug|id>     import, scaffold, start the clock
lc done [problem]        stop, mark solved, schedule the next review
lc session [--minutes N] a guided study block built from your own notes
lc sync / lc push        generate the repo, commit, push (nightly via launchd)

94 offline tests — no network, no fixtures pulled at runtime. Most of them are about the reconciliation matrix, because that's the part that can destroy work.
