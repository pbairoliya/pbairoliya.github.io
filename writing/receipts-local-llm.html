Scanning receipts into Obsidian with a local LLM

June 2026 · 6 min

I scan a receipt on my phone and, seconds later, my Obsidian vault updates itself: pantry, shopping list, and a monthly expense report. No cloud OCR, no API keys — Apple Vision and a local model, all on-device.

The interesting part isn't the receipts. It's the pattern: gather context → prompt a model → write the result back somewhere useful, with an index as the single source of truth so the whole thing is rebuildable.

The problem

Receipts are a small, constant friction. They pile up in a pocket or a junk drawer, and the things I actually want from them — what's in the pantry, what I need to buy, how much I spent this month — never get extracted, because extracting them by hand is exactly the kind of chore that doesn't survive a busy week.

I'd already built a couple of small AI tools for my vault, so I knew the shape of the fix: get the receipt into the vault once, let software do the parsing, and have the vault keep itself up to date. The goal wasn't a receipt app. It was to make the receipt disappear into useful state without me touching a spreadsheet.

The pipeline

iPhone scan ──iCloud──▶ Receipts/Inbox/*.pdf|png|jpg   (launchd watches the folder)
        │
   ocr.py (Apple Vision) ──▶ extract.py (gemma3 → store/date/time/type/total/items)
        │
   receipts.py ── fingerprint (store+date+time) → de-dup ──▶ .receipts.jsonl (source of truth)
        │                                                          │
   poor ink? → Review/<note>.md (I fix → status: ready)      (everything below derived each run)
        │                                          ┌──────────────┼───────────────┐
   groceries → pantry.py                       expenses.py    shopping.py    reminders_out.py
                                            Finance/Expenses/  Shopping List  Apple Reminders

I scan a receipt with the iOS document scanner — groceries, gas, a restaurant, anything — and it lands in an Inbox folder that syncs through iCloud. A background job notices the new file, runs OCR on it, hands the text to a local model that pulls out the store, date, total and line items, then writes the results into the right places. By the time I think to check, it's done.

Design call #1: on-device everything

OCR runs on Apple Vision, which ships with macOS — I call it straight from Python, and it reads PDFs, PNGs and JPEGs with no cloud service and no API key. The iOS scanner deskews and de-glares the image before it ever hits OCR, which noticeably improves accuracy.

The model is Ollama running gemma3:12b, also entirely on my machine. A stream of my grocery and spending data never leaves the laptop, there's nothing to pay per request, and there are no credentials to rotate. For a personal tool that touches finances, "it physically can't leak to a third party" was worth more than a slightly smarter cloud model.

Design call #2: an open taxonomy

The model does two jobs at once: it reads the receipt and decides what kind of expense it is. The easy version is a fixed list — groceries, dining, gas, rent — and a prompt that forces a choice.

I let it do something better. Common categories match via synonyms (a gas station maps to Car, a restaurant to Dining), but the model is allowed to invent a new category when nothing fits. Scan a haircut receipt and it creates a Haircut category, a folder, and a line in the expense report — no code change, no enum to update. Letting the model extend the taxonomy instead of choosing from a frozen one is the difference between a tool I have to maintain and one that absorbs whatever I throw at it.

Design call #3: the index is the source of truth

This is the decision that made everything else safe. There is one canonical file — .receipts.jsonl — and everything else is derived from it on every run: the pantry, the monthly expense reports, the per-store breakdown. The vault notes are disposable views; the index is the data.

That buys two things. Dedup: each receipt gets a fingerprint from its store, date and time, so scanning the same one twice keeps a single PDF and reconciles the numbers with item-level deltas instead of double-counting. And rebuildability: a separate reindex.py reconstructs the entire index — and from it, every report — out of the archived PDFs. Corrupt a note, or change how reports look, and I just regenerate.

"Derive, don't mutate" turned out to be the single most important rule in the project. Anything I edit by hand is something the next run can fight with.

Keeping a human in the loop

OCR on a faded receipt is not perfect, and I'd rather have a gap than a wrong number in my finances. So the pipeline checks itself: if the line items don't sum to within 10% of the printed total — or a price comes back null — the receipt is held in a Review/ folder instead of being trusted.

Fixing it is one tap. The review note has a native Obsidian checkbox (- [ ] ✅ Reviewed) that actually persists when I tick it on my phone; ticking it finalises the receipt on the next run. That detail matters more than it sounds — I first tried HTML checkboxes and learned the hard way that Obsidian doesn't save taps on those. For anything that needs to stick, use the real markdown checkbox.

Making it invisible

A tool I have to remember to run is a tool I'll stop running. So a launchd agent watches the Inbox folder and also fires once a day at 8am, which means a scanned receipt is usually processed within seconds of syncing.

Two small things made the automation robust. launchd starts jobs with a bare PATH, so I had to set it explicitly for the watcher to find ollama — and start it if it's down. And because the watcher and the daily run can overlap, main() takes an fcntl lock: Apple Vision does not enjoy being driven by two processes at once.

What I'd reuse

Strip away the receipts and the bones are the same loop I keep coming back to: gather some context, prompt a model, write the result back somewhere useful. The OCR is just an unusual context source; the open taxonomy is just a prompt that trusts the model a little more.

The two patterns I'll carry into the next project are index-as-source-of-truth with everything derived — it makes dedup, rebuilds and format changes trivial — and folder-watch automation via launchd, the cheapest way to make a tool feel ambient instead of manual. Both are general. The receipts were a good excuse to learn them.
